# The interview and the beat table

One message of questions, then build. Don't send menus of concepts; work from their words.

1. **What is it, in one line?** How they'd describe it to a friend.
2. **The one thing.** The feature the whole film exists to show. If they name five, ask which one sells it.
3. **The before/after.** A visible change a viewer can judge in one glance, and the real clicks that produce it, in
   order, the way a person would do them.
4. **What's on screen.** Their own demo content (documents, images, data, names). It must look like real use, not
   lorem ipsum. If something will be transformed on camera, ask for its finished version too: the finished state they
   like is the truth, not whatever the app does by default.
5. **Where it runs.** Repo or URL, how to start it locally, which accounts or keys can be placeholders. You work on a
   copy; their repo is never touched.
6. **Length and destination.** Where it will be posted (site hero, social, store page, a launch post) decides length
   and aspect. Treat a stated length as a ceiling; hand-speed actions and holds make the honest cut a bit longer.
7. **Sound.** Do they have a track, want none, or want an original score? (See music.md. Don't push it.)

## The beat table

| Time | Shot | Copy |
|---|---|---|
| 0-3 s | (what the camera sees, what moves) | (one short line) |
| ... | ... | ... |

Copy is short, one idea per line, in their words. It follows actions (caption windows name timing rows), so it never
needs re-timing by hand. When you write a line, read the line before it: each should continue the thought.

Show the table, wait for their go, then build the first beat and send stills before building the rest.
